# Motion Retargeting User Study

A static site that shows participants one source motion plus six retargeted
versions of it, and asks them to rank the versions on three criteria. Responses
are committed back into this repository and aggregated automatically.

- **Ranked methods:** ground truth, naive copy, HumanIK, SAN, R2ET, ReFM-HumanIK
- **Reference (never ranked):** the original source motion
- **Criteria:** overall quality, self-penetration, semantic preservation
- **Ties are allowed** — participants may give two results the same rank
- **Blinded** — methods are relabelled A–F in a fresh random order on every
  clip, for every participant

Results land in [`results/aggregate.md`](results/aggregate.md).

---

## Layout

```
index.html                    the study
assets/app.js                 study logic (blinding, ranking, submission)
assets/config.js              ← the only file you normally edit
assets/clips.json             generated; do not edit by hand
videos/<method>/<clip>.mp4    stimuli
scripts/build_manifest.py     regenerate clips.json after changing videos
scripts/aggregate.py          responses → aggregate.json + aggregate.md
worker/                       Cloudflare Worker that commits responses
results/responses/*.json      one file per completed session
results/aggregate.{json,md}   generated by CI on every new response
.github/workflows/            re-runs the aggregation automatically
```

## Setup

### 1. Publish the site

Push this repository to GitHub, then **Settings → Pages → Source: Deploy from a
branch**, branch `main`, folder `/ (root)`. The site appears at
`https://<user>.github.io/<repo>/`.

### 2. Deploy the submission Worker

GitHub Pages is static hosting: the browser cannot write into this repository by
itself. A small Cloudflare Worker does it, holding the GitHub token server-side
so no credential is ever exposed to participants. Cloudflare's free tier is
ample for a user study.

Create a **fine-grained personal access token** scoped to *this repository only*
with `Contents: Read and write`, then:

```bash
cd worker
# edit wrangler.toml: GITHUB_REPO, ALLOWED_ORIGIN
npx wrangler secret put GITHUB_TOKEN     # paste the token; never commit it
npx wrangler deploy
```

Copy the deployed URL into `assets/config.js`:

```js
submitEndpoint: "https://refm-user-study.<your-subdomain>.workers.dev",
```

Commit and push. `ALLOWED_ORIGIN` must exactly match your Pages origin
(e.g. `https://alice.github.io`) or submissions are refused — this is what stops
the endpoint being used as an open write channel into the repo.

### 3. Check it works

Open the site, complete a session, and confirm a new file appears under
`results/responses/`. The **Aggregate study responses** workflow then runs and
updates `results/aggregate.md`.

---

## Running without a Worker

Leave `submitEndpoint` empty. Participants get a JSON file to download and send
you. Drop the files into `results/responses/` and run:

```bash
python3 scripts/aggregate.py
```

This is also the automatic fallback if the Worker is unreachable mid-study, so a
network failure at the final step never costs you a completed session.

## Configuration

`assets/config.js`:

| Key | Meaning |
|---|---|
| `submitEndpoint` | Worker URL. Empty ⇒ offline download mode. |
| `clipsPerParticipant` | Clips shown per participant. `0` = all. Clips are drawn at random, so coverage evens out across participants. |
| `estimatedMinutes` | Shown on the intro screen. |
| `allowResume` | Let a participant who closes the tab continue where they left off. |
| `downloadOnFailure` | Fall back to a file download if submission fails. |

Budget roughly 40–60 seconds per clip. With 15 clips that is 10–15 minutes; if
you recruit non-experts, set `clipsPerParticipant` to 6–8 and recruit more
people instead.

## Changing the stimuli

Add or remove files under `videos/<method>/`, then:

```bash
python3 scripts/build_manifest.py
```

A clip is included **only if every method has it**, so a participant can never
be shown an incomplete comparison. The script prints anything it skipped and
why — useful for catching a half-finished render.

## Reading the results

`results/aggregate.md` reports three numbers per method per criterion.

**`Mean rank`** (lower is better) is the headline figure. Because ties are
allowed, it is sensitive to how widely each participant spreads their ranks: a
participant who marks everything `1` drags all methods toward 1.

**`Norm.`** rescales ranks to `[0, 1]` within each participant-clip-criterion
before averaging, so a participant's personal tie habits cancel out. A
participant who gave every method the same rank contributes `0.5` to each rather
than arbitrarily counting as best or worst.

**`Win rate`** is the share of strict pairwise comparisons within a clip that the
method won, ties excluded. It is scale-free.

Report mean rank as the primary result and expect the three to agree on the
ordering. If they disagree, a few participants are using the scale unusually —
inspect the per-response files before drawing conclusions.

## Notes on validity

- **Blinding**: method identity never reaches the browser as a label. The
  letter↔method mapping is regenerated per clip and stored with each response,
  so it is fully reconstructible at analysis time.
- **Order effects**: both the method→letter assignment and the clip order are
  shuffled per participant.
- **No partial data**: nothing is transmitted until the participant submits, and
  every criterion must be fully ranked before advancing.
- Responses contain no names or emails. They do record a user-agent string and
  coarse self-reported expertise; mention this if your institution requires
  disclosure.
